How SAM tags, analyses and stores collateral

Companion to sam-how-it-works.html. Traced from the code (web/lib/sharepoint.ts, web/lib/cards.ts, prototype/carding_prep.py, the nightly carding skill, the docs/supabase-*.sql migrations), with numbers read from the live Supabase database today.

1 · The whole system on one page

Two feeds fill the database. A nightly snapshot records where every file is and tags it from its folder and filename. A nightly carding job has Claude read new or edited documents and write a card describing what each one says. Views merge the two into one catalogue, and every channel answers from that catalogue.

2 · How a file gets tagged and categorised

Tagging happens in three layers. Each one corrects the one before it, and the third layer decides whether a file can appear in answers at all.

2a · Layer 1: rule tags from the folder and filename (every file, every night)

Nothing is read at this stage. A tag means "the library says so". If the folder and the filename disagree on type, the folder wins, because filing a document in a folder is a deliberate choice. Code: tagsFor() in web/lib/sharepoint.ts, a copy of prototype/sp_tags.py.

2b · Layer 2: card tags from reading the document (carded files only)

For the 317 carded files, Claude reads the text and sets type, industry, products, competitors, personas and regulations from what the document actually says (full list in §3). When a file has both, SAM keeps the richer record, which is almost always the card. Two things are fixed whichever record is kept: the year read from the document body beats a filename year, and the real SharePoint link and folder always come from the registry. Code: merge() in web/lib/cards.ts.

2c · Layer 3: versions and eligibility, which decide what can be answered

The database groups copies of the same document into a family (same name stem with a different version, edition or language), then runs every asset through the checks below, top to bottom. The SQL lives in docs/supabase-sam-asset-families.sql, with the same rules in web/lib/family.ts.

3 · How a document is analysed: the card

The carding job runs every night at 07:00 IST (/sam-nightly-carding). It takes files from the carding queue, meaning files that are uncarded, changed since their card or renamed, up to 15 a night, newest version of a document first. Older copies of documents that already have a card are skipped. Each file is copied from OneDrive and its text extracted (PDF, DOCX, PPTX, XLSX). Claude then reads that text and fills in these fields:

Rules Claude follows

  • Never invent numbers, clients or outcomes that aren't in the text
  • No passwords, phone numbers, bank details, personal emails, customer IDs or IP addresses. Note that they exist ("contains staff phone numbers") without copying them.
  • Little or no text: card from the title and folder with confidence ≤ 0.5, and say so

Gates before loading

  • compare_cards.py: sanity check against existing cards
  • Valid JSON and a scan for sensitive data
  • load_cards.py --dry-run, then load, then --check: 0 missing, 0 extra, 0 title differences

The boundary

  • Only Claude reads document bodies
  • Only the card goes to Supabase, so you can read every row and see exactly what the answering model sees
  • Cards are also committed to git as corpus/cards/*.json

4 · How a question is matched to documents

The search runs over the 233 answerable assets only. First the filters (type, vertical, product, "for a customer" → public only), then each remaining card is scored on its title, type, industry, products, brief, use_for and so on. Code: searchAssets() in web/lib/cards.ts.

score = 2 × query words found + 1.5 × words found in the title + 6 if every word matched + 3 if a type word matched alongside something else + 0.4 if under 2 years old − demotion Demotion applies only when at least 2 reps rated an asset "wrong asset" for the same topic and nobody rated it helpful. It fades after 60 days. Each document gets one slot: the shareable edition when the rep wants to send it. The rep's own words are always searched first, before the model's search terms.

Model step

The model reads the top cards and returns a verdict plus the numbers of the documents it picks. Fallback order: gpt-6-luna → Groq 120b → Groq 20b → retrieval only. Each question costs ~1.3k tokens.

Guard step

SAM writes every document line, link and "safe to send" line from the card itself. Verdicts that name documents not in the results get replaced. A denial that names nothing is logged as a content gap.

Gap step

If nothing fits, SAM offers real substitutes plus an Ask marketing button. The request goes to sam_content_requests, ranked by how many different reps asked.

5 · Everything Supabase stores

All tables live in the accops-marketing-dashboard project and are prefixed sam_. Row-level security is on with no public rules, so only the server key can read or write them. No document bodies are stored, only where each file is and what its card says.

6 · Where the structure needs work

Two tag lists that don't match

Layer 1 and layer 2 use different words for the same thing: Competitive vs Battlecard, Solution Brief vs Solution Document. Card industries are free text, with three versions of Government and four of IT. Only 79 of 875 files have a rule-based industry. Fix: one fixed list per facet, enforced by the database.

Loose card-to-file link

Cards are keyed on a path on this laptop, not the SharePoint item_id, and the database doesn't enforce the link. 4 SharePoint cards are linked to no file. Visibility is called both in cards but public in the view. Fix: make item_id required and enforced for SharePoint cards.
