How SAM works

Three views of SAM, traced from the code in web/ and prototype/ rather than from the design doc. The numbers come from the live database today.

1 · Two pipelines feed one catalogue

SAM has two separate sources of knowledge. One updates itself and records where each file is. The other is written by hand and records what the file says. Every answer comes from the two merged together.

Have we mapped it?

Half of it

  • Links and filing: yes, and it runs by itself. A new or edited file reaches SAM within a minute or so, with its real SharePoint link.
  • What a file says: no. Carding is done by hand, and nothing tells you that a new file needs a card.
  • Deletions: the design exists, but it's blocked. See section 3.

Pipeline A

Automatic: location and link

  • Power Automate watches Sales Collateral on your login
  • Each add or edit is sent to /api/channels/sharepoint
  • Tags are guessed from the folder and filename. The file itself is never opened
  • SAM refreshes its copy every 5 minutes

Pipeline B

By hand: what the file says

  • You download the file
  • extract_text.py pulls out the text
  • Claude writes the card (corpus/cards/batch-*.json)
  • compare_cards.py quality check
  • load_cards.py uploads the cards to Supabase

2 · What happens when someone asks a question

This shows the web chat. WhatsApp, REST and MCP go through the same steps; only the way in differs (see the cards below). The whole trip normally takes 1.5 to 3 seconds.

Frontend

What the rep's screen does

  • The catalogue panel is built on the server from the same allAssets(). No model is involved
  • The chat sends the question and the last 6 turns to /api/ask
  • The answer shows a one-line verdict and up to 3 asset cards with links
  • Clicking a link is logged through /api/open
  • A "How SAM got there" panel shows each search the model ran
  • Three feedback buttons are saved through /api/feedback

Privacy

What Groq actually sees

Only the search results: title, type, industry, the client description, up to 300 characters of summary, up to 4 outcomes, and the trust note (expired, newer edition available, or old).

It never sees file text or the real client name. client_actual is never read from the database at all.

Other ways in

Same steps, different front door

  • WhatsApp: Meta calls a webhook. SAM checks the signature, maps the phone number to a user, keeps 6 hours of history, and replies after acknowledging Meta
  • REST / MCP: each caller needs its own access token, and it runs the same apiAsk(). MCP's search_assets skips the model entirely
  • If Groq fails: SAM falls back to plain search with a stock sentence, and the trace panel says so

Gap 1 · contents

Nothing tells you what needs carding

The registry already knows which files have no card. Cards have an updated_at date, so it can also tell which files changed after their card was written. Nothing shows you either list.

Smallest fix (not built): a "needs carding" list on the admin dashboard, built from one database query. You'd still card by hand, in batches, but you'd have a to-do list.

Gap 2 · deletions

Two ways out

  • Ask IT to allow SAM through the Graph policy, or to give the delete flow a site-admin login
  • Avoid IT (untested): a daily Power Automate flow that lists every file in the folder and sends the list to SAM. SAM marks anything missing from the list as deleted. It runs on the same login that already works for the change flow, so it needs neither Graph nor admin rights
